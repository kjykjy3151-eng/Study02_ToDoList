# 할 일 관리 앱 — PRD

| | |
|---|---|
| 상태 | 설계 승인 완료 |
| 작성일 | 2026-10-05 |
| 범위 | 1차 구현 전체 |
| 갱신 | 2026-10-09 — 최근 7일 성과 표, 카테고리 탭 백분율, 100% 달성 문구, 데스크톱 2단 레이아웃 추가 |

## 1. 배경과 목적

하루 10~20개 규모의 할 일을 혼자 관리하기 위한 개인용 웹 앱이다. 설치나 로그인 없이 브라우저에서 파일을 열면 바로 쓸 수 있고, 새로고침하거나 브라우저를 닫았다 열어도 입력한 내용이 남아 있어야 한다.

성공 기준은 단순하다. **할 일을 추가하고 완료 체크하는 데 걸리는 동작이 최소여야 하고, 지금 얼마나 처리했는지가 화면을 보는 순간 드러나야 한다.**

### 전제

- 사용자는 한 명이다. 계정, 권한, 공유 개념이 없다.
- 한 기기, 한 브라우저에서 사용한다. 기기 간 동기화는 하지 않는다.
- 서버가 없다. 모든 데이터는 브라우저 안에 머무른다.

## 3. 데이터 모델

할 일 하나는 다음 형태의 객체다.

```js
{
  id:        "lx8k2p_a9f3c1",   // 생성 시각(36진수) + 난수 6자
  text:      "주간 보고서 작성",
  category:  "업무",             // "업무" | "개인" | "공부"
  done:      false,
  dueDate:   "2026-10-07",       // YYYY-MM-DD, 미지정이면 null
  completedAt: null,             // 완료한 날 YYYY-MM-DD, 미완료면 null
  createdAt: 1760000000000       // Date.now()
}
```

### 필드 규칙

- `id` — `Date.now().toString(36) + "_" + Math.random().toString(36).slice(2, 8)`. `crypto.randomUUID()`는 사용하지 않는다. 이 API는 보안 컨텍스트를 요구하는데 `file://`에서의 동작이 브라우저마다 갈리기 때문이다. 시각과 난수를 조합하면 같은 밀리초에 두 건을 추가해도 충돌하지 않는다.
- `category` — 위 세 값으로 고정한다. 사용자가 카테고리를 추가하거나 이름을 바꾸는 기능은 넣지 않는다.
- `dueDate` — 문자열로 저장한다. `<input type="date">`의 값 형식과 같아서 변환이 필요 없고, 문자열 비교만으로 날짜 정렬이 된다.
- `completedAt` — 이 할 일이 **어느 날의 완료 수로 세어졌는지**를 가리킨다. 완료하면 그날 날짜, 완료를 취소하면 `null`이다. 일일 기록(아래)만으로는 "월요일에 완료한 것을 수요일에 취소했을 때 어느 날에서 1을 빼야 하는지"를 알 수 없어서 필요하다. 이 필드가 생기기 전에 저장된 할 일에는 없으므로, 없는 값은 `null`로 취급하고 그 할 일을 버리지 않는다.
- 날짜는 모두 **로컬 시간**의 `YYYY-MM-DD`다. `toISOString()`은 UTC로 변환해서 한국 시간 늦은 밤의 완료가 전날로 기록되므로 쓰지 않고, `getFullYear()`, `getMonth() + 1`, `getDate()`로 0을 채워 만든다.
- `createdAt` — 정렬의 최종 기준으로만 쓴다. 화면에 표시하지 않는다.

### 일일 기록

날짜별 완료 건수를 세는 별도 객체다.

```js
{ "2026-10-09": 5, "2026-10-08": 3 }
```

| 동작 | 일일 기록 | `completedAt` |
|---|---|---|
| 완료로 바꿈 | 오늘 날짜 값에 1을 더한다 | 오늘 날짜 |
| 미완료로 되돌림 | `completedAt` 날짜 값에서 1을 뺀다(0 아래로는 내려가지 않는다) | `null` |
| 삭제 | 바꾸지 않는다 | (항목과 함께 사라짐) |

기록과 `completedAt`은 서로 대체할 수 없다. 기록은 항목이 삭제된 뒤에도 남는 누적값이고, `completedAt`은 되돌릴 때 어느 날 값을 줄일지 알려 준다. `completedAt`이 없는 완료 항목(필드가 생기기 전에 완료한 것)은 기록에 센 적이 없으므로 되돌려도 기록을 건드리지 않는다.

기록은 정리하지 않는다. 10년치를 쌓아도 약 70KB로 한도(약 5MB)의 일부이고, "삭제해도 성과는 남는다"가 사용자가 고른 동작이다.

### 저장

localStorage의 `todos.v1` 키에 위 객체의 배열을, `dailyLog.v1` 키에 일일 기록 객체를 JSON 문자열로 저장한다. 키에 버전을 붙여두면 나중에 필드 구조가 바뀌어도 기존 데이터를 식별해 마이그레이션할 수 있다.

쓰기 시점은 데이터가 바뀌는 모든 동작(추가, 수정, 삭제, 완료 토글) 직후다. 완료 토글은 두 키를 함께 쓴다. 필터 전환은 데이터를 바꾸지 않으므로 저장하지 않는다.

## 4. 화면 설계

넓은 화면(너비 860px 이상)에서는 두 단이다. 왼쪽에 입력과 요약, 오른쪽에 목록을 둔다.

```
┌─────────────────────────────┬───────────────────────────────────┐
│  할 일               7 / 18 │  ☐  주간 보고서 작성   업무  10/07 ✕ │
│  ████████████░░░░░░░  38%  │  ☐  장보기             개인        ✕ │
│  🎉 모든 할 일을 완료했습니다. │  ☑  ~~운동 30분~~      개인        ✕ │
│                             │                                   │
│  최근 7일 성과               │                                   │
│   화  수  목  금  토  일 [월]  │                                   │
│   2   0   4   1   0   3  [5]  │  ← 오늘 칸을 강조               │
│  [ 새 할 일 입력...      ]   │                                   │
│  [개인▾] [날짜] [추가]       │                                   │
│  전체 18  업무 3/7 (42%)    │                                   │
│  개인 2/6 (33%) 공부 2/5 (40%)│                                  │
│  ● 전체   ○ 미완료   ○ 완료  │                                   │
└─────────────────────────────┴───────────────────────────────────┘
```

(달성 문구는 100%일 때만 나타난다. 위 그림은 자리를 보이려고 함께 그렸다.)

좁은 화면에서는 한 단으로 쌓인다. 순서는 왼쪽 단의 위에서 아래, 그다음 오른쪽 단이다: 제목과 진행률, 달성 문구, 7일 표, 추가 폼, 카테고리 탭, 상태 필터, 목록.

### 4.1 추가 폼

입력창, 카테고리 선택(기본값 `개인`), 마감일 선택으로 구성한다. 입력창에서 Enter를 누르면 추가된다. 추가 후 입력창은 비워지고 포커스가 유지되어, 연속으로 여러 건을 입력할 수 있다.

추가 후 **카테고리 선택값은 유지하고, 마감일은 비운다.** 같은 카테고리의 할 일을 연달아 넣는 경우는 많지만, 날짜가 남아 있으면 다음 항목에 의도치 않은 마감일이 붙는다.

### 4.2 목록 정렬

1. 미완료 항목이 먼저, 완료 항목이 뒤
2. 같은 그룹 안에서는 마감일이 빠른 순. 마감일이 없는 항목은 있는 항목보다 뒤
3. 마감일이 같거나 둘 다 없으면 `createdAt` 내림차순 (나중에 추가한 것이 위)

### 4.3 수정

할 일 텍스트를 클릭하면 그 자리가 입력창으로 바뀐다. 편집을 끝내는 경로는 세 가지다.

| 동작 | 결과 |
|---|---|
| Enter | 저장하고 편집 종료 |
| Esc | 변경을 버리고 편집 종료 |
| 포커스 이탈 | 저장하고 편집 종료 |

Esc는 편집 상태를 먼저 해제한 뒤 원래 텍스트를 복원한다. 그래야 뒤따라 발생하는 포커스 이탈이 저장으로 처리되지 않는다.

내용이 빈 문자열이 되면 저장하지 않고 원래 텍스트를 유지한다. 빈 제목의 할 일은 목록에서 식별할 수 없다. 삭제는 `✕` 버튼의 역할이다.

수정 대상은 텍스트뿐이며, 카테고리와 마감일 변경은 1차 범위에 넣지 않는다.

### 4.4 삭제

각 항목 오른쪽의 `✕` 버튼을 누르면 즉시 삭제된다. 확인 대화상자는 두지 않는다. 혼자 쓰는 앱이고 한 줄을 다시 입력하는 비용이 확인 절차의 비용보다 낮다. 완료한 항목을 삭제해도 일일 기록은 줄지 않는다.

### 4.5 필터

카테고리 축(전체 / 업무 / 개인 / 공부)과 상태 축(전체 / 미완료 / 완료)이 있고, **두 축은 AND로 함께 적용된다.** "업무 + 미완료"처럼 조합할 수 있다.

기본 상태는 카테고리 `전체`, 상태 `전체`다. 상태 기본값을 `미완료`로 두면 완료 항목이 처음부터 숨겨지는데, 그러면 "완료 항목을 목록 아래로 내린다"는 4.2의 정렬 규칙이 기본 화면에서 아무 역할도 하지 못한다. 완료한 일이 눈에 보이는 것 자체가 진행 상황의 일부다.

필터 선택값은 저장하지 않는다. 새로고침하면 기본값으로 돌아간다.

### 4.6 빈 상태

필터 결과가 0건이면 목록 영역에 안내 문구를 표시한다. 전체가 0건일 때와 필터 때문에 0건일 때의 문구는 구분한다.

### 4.7 최근 7일 성과

진행률 아래에 표를 하나 둔다. **오늘로 끝나는 최근 7일**이고, 가장 오래된 날이 왼쪽, 오늘이 오른쪽 끝이다. 칸마다 한글 요일 한 글자(일 월 화 수 목 금 토)와 그날의 완료 건수를 보여 준다. 기록이 없는 날은 `0`이다. 오늘 칸은 배경색과 굵은 테두리로 구분한다.

7일보다 오래된 기록은 표에 나오지 않지만 저장소에는 남는다. 표는 일일 기록만 읽으며, 할 일 목록과 필터에 영향을 받지 않는다.

### 4.8 100% 달성 문구

모든 할 일이 완료되면 진행률 바로 아래에 이모지와 짧은 문장(`🎉 모든 할 일을 완료했습니다.`)을 보인다. **할 일이 하나 이상일 때만** 나타난다. 빈 목록은 `0 / 0`, 0%이고 이것은 달성이 아니다. 완료를 취소하거나 미완료 항목을 추가하면 다시 사라진다. 필터와 무관하게 전체 데이터로 판단한다.

### 4.9 레이아웃

너비 860px 이상에서 두 단으로 나눈다. 왼쪽(360px 고정)에 제목, 진행률, 달성 문구, 7일 표, 추가 폼, 카테고리 탭, 상태 필터를 두고, 오른쪽에 목록과 빈 상태 안내를 둔다. 860px 미만에서는 한 단으로 쌓이며 순서는 4절 첫머리와 같다. 카테고리 탭은 글자가 길어져(`업무 3/7 (42%)`) 폭이 모자라면 다음 줄로 넘어간다.

## 5. 진행률

- **전체 진행률** — 완료 수 / 전체 수. 백분율과 `7 / 18` 형태의 숫자를 함께 표시한다.
- **카테고리별 진행률** — 카테고리 탭에 `3/7 (42%)` 형태로 완료 수, 전체 수, 백분율을 표시한다. 백분율은 전체 진행률과 같은 규칙(내림)을 쓴다. `전체` 탭은 전체 개수만 보여 준다.

**모든 수치(달성 문구 포함)는 필터와 무관하게 항상 전체 데이터로 계산한다.** 필터를 걸었을 때 진행률이 따라 변하면, 전체 상황을 확인하려고 매번 필터를 풀어야 한다. 진행률의 역할은 "지금 얼마나 처리했나"를 한눈에 보여주는 것이므로 맥락에 따라 흔들려서는 안 된다.

항목이 하나도 없으면 바는 0%, 숫자는 `0 / 0`으로 표시하고 카테고리 탭은 `0/0 (0%)`가 된다. 0으로 나누는 연산이 발생하지 않도록 분모가 0인 경우를 분기한다.

## 6. 기술 구조

### 파일 구성

```
index.html    마크업
style.css     스타일
app.js        전체 로직
```

빌드 도구와 외부 의존성이 없다. `index.html`을 더블클릭해 `file://`로 열면 바로 동작한다.

### ES 모듈을 쓰지 않는 이유

`<script type="module">`은 `file://`로 열린 문서에서 브라우저 CORS 정책에 막혀 로드되지 않는다. 모듈 단위로 파일을 쪼개면 로컬 HTTP 서버를 띄워야 하는데, 이는 "브라우저에서 바로 실행"이라는 핵심 요구사항(R7의 전제)을 깨뜨린다. 이 규모(JS 450줄 안팎)에서 모듈 분리로 얻는 이득이 실행 편의성을 잃는 대가보다 작다.

따라서 `app.js`는 일반 스크립트 한 개이며, 그 안에서 구역을 나눈다.

### app.js 내부 구성

| 구역 | 책임 |
|---|---|
| 저장 | localStorage 읽기, 쓰기(할 일, 일일 기록), 손상 데이터 처리 |
| 상태 | 할 일 배열과 현재 필터값 보관 |
| 순수 함수 | 정렬, 필터링, 진행률 집계, 최근 7일 집계 — DOM을 참조하지 않음 |
| 렌더 | 상태를 받아 DOM을 다시 그림 |
| 이벤트 | 사용자 입력을 상태 변경으로 연결 |

**정렬, 필터링, 진행률 집계는 DOM에 접근하지 않는 순수 함수로 분리한다.** 입력을 받아 값을 돌려주기만 하므로, 이후 테스트를 붙이고 싶어지면 브라우저 없이 바로 검증할 수 있다.

렌더링은 상태가 바뀔 때마다 목록 영역을 전부 다시 그리는 방식으로 한다. 20개 규모에서 부분 갱신 최적화는 체감 차이가 없고 코드만 복잡해진다.

## 7. 에러 처리

실제로 발생하는 두 가지만 다룬다.

### 저장된 데이터가 손상된 경우

`JSON.parse`가 실패하거나 결과가 배열이 아니면, 손상된 원본 문자열을 `todos.v1.broken` 키로 옮긴 뒤 빈 목록으로 시작한다. 그냥 덮어쓰면 복구 가능성이 사라지는데, 다른 키로 옮기는 처리는 몇 줄이면 된다.

`dailyLog.v1`도 같은 방식이다. 파싱에 실패하거나 객체가 아니면 `dailyLog.v1.broken`으로 옮기고 빈 기록으로 시작한다. 객체 안에서 날짜 형식이 아니거나 0 이상의 정수가 아닌 항목은 그 항목만 버린다.

### 빈 내용으로 추가 시도

입력값을 `trim()`한 결과가 빈 문자열이면 추가하지 않고, 입력창에 포커스만 유지한다. 경고 메시지는 띄우지 않는다.

### 다루지 않는 것

- **용량 초과** — 할 일 20개의 JSON은 수 KB 수준이고 localStorage 한도는 약 5MB다. 발생할 수 없는 상황에 대한 처리는 넣지 않는다.
- **네트워크 오류** — 서버가 없다.
- **localStorage 접근 차단** — 시크릿 모드나 브라우저 설정으로 저장이 막힌 환경은 1차 범위 밖이다 (9절 참조).

- [ ] `dailyLog.v1` 값을 `{{{`처럼 깨뜨린 뒤 새로고침하면, 7일 표가 모두 0이고 `dailyLog.v1.broken`에 깨진 값이 남아 있다
- [ ] `completedAt` 필드가 없는 예전 형식의 할 일이 `todos.v1`에 들어 있어도 새로고침 후 사라지지 않고 보인다

### CRUD

- [ ] 값이 0인 날의 완료를 취소해도 0 아래로 내려가지 않는다
- [ ] 완료한 항목을 삭제해도 표의 값이 줄지 않는다

## 9. 범위 밖

1차 구현에 포함하지 않는다.

| 항목 | 비고 |
|---|---|
| 계정, 로그인, 기기 간 동기화 | 서버가 필요하다 |
| 하위 할 일, 반복 일정 | 데이터 모델이 복잡해진다 |
| 알림, 리마인더 | 브라우저 권한과 백그라운드 동작이 필요하다 |
| 카테고리 추가 및 편집 | 세 개로 충분하다 |
| 태그, 검색 | 20개 규모에서는 눈으로 찾는 것이 빠르다 |
| 드래그 재정렬 | 정렬 규칙으로 대체한다 |
| 다크 모드 | 요청 범위에 없다 |
| 데이터 내보내기 및 가져오기 | 아래 리스크 참조 |

### 알려진 리스크: 데이터 소실

localStorage는 브라우저 설정에서 "사이트 데이터 삭제"를 실행하면 함께 지워진다. 백업 수단이 없으므로, 데이터가 쌓인 뒤 이런 일이 생기면 복구할 방법이 없다.

1차 범위에서는 의도적으로 제외한다. 데이터가 쌓여 소실이 아깝게 느껴질 시점이 오면, JSON 내보내기 및 가져오기 버튼을 추가하는 후속 작업으로 처리한다. 이는 기존 설계를 바꾸지 않고 덧붙일 수 있는 범위다.

## 10. 설계 근거 요약

판단이 갈릴 수 있었던 지점과 선택 이유를 남긴다.

| 결정 | 이유 |
|---|---|
| 날짜별 목록이 아닌 단일 목록 + 선택적 마감일 | 날짜별로 묶으면 미완료 항목을 다음 날로 넘기는 규칙이 추가로 필요하다. 마감일 필드가 같은 효용을 더 적은 규칙으로 낸다 |
| 진행률은 필터와 무관하게 전체 기준 | 맥락에 따라 흔들리는 진행률은 전체 상황 확인을 위해 매번 필터 해제를 요구한다 |
| 완료 항목을 아래로 내리고 유지 | 자동 삭제는 되돌릴 수 없다. 필터로 숨기면 원할 때 다시 볼 수 있다 |
| ES 모듈 미사용 | `file://` 즉시 실행이 요구사항이고, 모듈은 CORS로 막힌다 |
| 삭제 확인 대화상자 없음 | 혼자 쓰는 앱에서 한 줄 재입력 비용 < 매번 확인하는 비용 |
| 부분 갱신 없이 전체 재렌더 | 20개 규모에서 체감 차이가 없고 코드만 복잡해진다 |
| 일일 기록과 `completedAt`을 함께 둠 | 기록만 있으면 이전 날 완료한 것을 되돌릴 때 어느 날에서 뺄지 모르고, `completedAt`만 있으면 삭제한 항목의 성과가 사라진다 |
| 일일 기록을 정리하지 않음 | 10년치가 약 70KB이고, 사용자가 "기록은 남는다"를 선택했다 |
| 날짜를 로컬 시간 문자열로 만듦 | `toISOString()`은 UTC라서 한국 시간 늦은 밤의 완료가 전날로 기록된다 |
| 핵심 로직을 순수 함수로 분리 | 테스트 러너가 없는 지금도 구조가 명확하고, 필요해지면 바로 테스트를 붙일 수 있다 |
